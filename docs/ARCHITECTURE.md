# Architecture

Glass Notes uses one Expo / React Native / TypeScript application. Phone use targets mobile browsers; Windows and macOS Tauri hosts load the same static Web export. Application adapters target Web and Tauri only; native mobile development and iOS export have been removed. There is no application backend, account service or runtime model API.

## Code layout

| Directory | Responsibility |
| --- | --- |
| `src/app` | Expo Router routes and provider composition |
| `src/features` | Screens and shared interface components |
| `src/domain` | Search, recommendations, recipe snapshots, calculations and validation |
| `src/content` | Bundled recipes, bottles, ingredients, translations and source records |
| `src/platform` | Local storage, file access, restore coordination and platform adapters |
| `src/i18n`, `src/theme` | Eight-language interface text and visual tokens |
| `src/media`, `assets` | Bundled images, thumbnails, maintained brand sources and provenance |
| `public/brand`, `src-tauri/icons` | Ignored icon outputs generated from `assets/brand` by Web/desktop entry points |
| `src-tauri` | Windows/macOS host, storage bridge, capabilities and installer configuration |
| `scripts` | Development, verification, content authoring and packaging commands |

## Content boundaries

A cocktail owns its card identity and can have several independent source versions. Search conditions must be satisfied by one version, never by combining facts from different versions. Results carry the selected version ID into details.

Runtime records live in `src/content`; recipe collections are named by source or content under `recipe-collections/`. Offline research is not imported into the app. Tests also use reviewed provenance fixtures. Public display translations do not rewrite stored recipe fingerprints or user-authored titles. Image provenance, recipe sources, translations and editorial flavour inference are separate records.

The material directory uses reviewed concepts over stable legacy ingredient IDs. Pure spirit styles share a main entry; flavored, infused and prepared materials remain separate. Ordinary saline has one entry, with concentration and original doses retained in each source recipe. Unreviewed identities fall back to exact matching; names, aliases and taxonomy parents cannot infer equivalence. Source-row alternatives and display labels require an unchanged full original row. Legacy aliases retain unknown language and provenance when their language cannot be proved.

Cabinet addition planning uses the shared source-row material resolver, including explicit ingredient and brand mappings from owned bottles. It enumerates one-material or unordered two-material purchases that satisfy the unmet candidate sets; every suggested addition must be required by an actually unlocked version. Drinks already covered by any source version are excluded from gains. All new versions, brand/preparation checks and optional missing materials remain attached to their source; counts group by cocktail. Joint gains compare adding the chosen pair with adding either member alone. Plans are derived local views and do not write inventory or add storage/backup keys.

Cabinet planning offers count coverage by default and an optional taste goal using the same bulk Bayesian version scorer as discovery. It uses stable posterior means, with material readiness and explicit local context tiers ahead of personal utility; each newly unlocked cocktail contributes at most one eligible source from its highest available tier. Recipe filters constrain candidates without hiding already-owned sources from the baseline. Preferences use only saved feedback, with honest cold-start/read-failure count fallbacks and failed-write retry. A component-owned bounded cache separately reuses enumeration, scoring, context and final ordering; complete input-value identities invalidate it after material, brand, recipe, evidence or feedback edits, and recovery remounts discard it. Purchase-name search and pagination do not refit the model. Preference hints stay inside the existing collapsed source details. No sampling, new inventory writes or persistent model is added to planning.

Research topics distinguish complete published recipes from retained source gaps. Selected international-competition works include serving measures, methods, authors and direct organizer sources; bespoke preparations remain separate from the finished drink. Cross-year selections carry an explicit year range and each work's actual year. Name-only and undosed ingredient-list records are not recipe cards. Research recipes do not automatically become catalogue versions or inferred cabinet ingredients. Maintained factual provenance and redistribution limitations remain under `research/competitions/`.

## Personal records

Root providers stay mounted across route changes. Business keys cover preferences, favourites and lists, cupboard materials, owned bottles, experiments, private recipes, backup references, making sessions, taste experiences and shopping. Platform adapters retain explicit loading, failure and retry states.

Shopping is a separately versioned category at `glass-notes.shopping.v1`. It freezes selected recipe snapshots, guarded source labels and actual canonical purchase candidates. Only required missing rows create purchases; a source-row alternative selects one ingredient, and common purchases are merged with their contributing rows. Reading never regenerates the saved list. Removal dismisses contributing requirements; ordinary edits cannot change bought status. The normal parser rejects unsafe nested properties and enforces 500 targets, 5,000 items/total row references and 5,000,000 UTF-8 bytes. The recipe-detail action is directly visible beside the main mixing/order actions, adds the currently selected source version, and opens shopping after a confirmed save. Discovery keeps its original recipe cards without shopping controls. Recipe choices and saved target headers reuse existing drink thumbnails, with a compact localized placeholder when an older saved recipe has no media; images do not change frozen recipe identities.

Purchase confirmation flushes personal providers and journals shopping plus cupboard values together, checking the complete raw before-state, generation and readback. Prepared interruptions roll both categories back; committed interruptions retain both. A durable bought flag makes retries idempotent, including after an intentional later cabinet removal. Purchase-specific recovery notices distinguish success and rollback from backup restore. The personal-store epoch recreates providers after a transaction; the navigation root state is retained so the route, query and back stack can be restored after the navigator remounts. New purchase journals use an optional notice field: older binaries reject an unfinished new journal, so complete recovery in the newer app before downgrading.

Saved recipes keep exact snapshots. Making state writes schema 2 and reads schemas 1 and 2 through the original storage key; reading does not migrate saved records. New sessions freeze source labels, allowed material candidates and actual supply bindings independently of the recipe fingerprint. Old sessions retain their original exact rules and can resume the saved source version after catalogue changes. Readiness reviews also include the new material semantics. Quantities belong to actual supplies: shared claims accumulate against one stock, ambiguous old stocks are never summed, and deductions recheck ownership and frozen bindings. Multiple legacy stock rows mapped to one bottle keep their values but cannot establish its quantity or permit new automatic deductions. Source brand requirements apply to the frozen original candidate family; an explicitly allowed different source alternative does not inherit that brand. Matching indexes are reused only within one synchronous catalogue operation; public resolver calls observe subsequent catalogue changes. Full backup schema 3 and other personal-category schemas stay unchanged. Private recipes append revisions on Save; experiments autosave. Optional private photos are compressed local JPEG data URLs, bounded to 200,000 characters.

Drink strength is a pure derived view over an exact recipe or saved making snapshot. Curated producer examples and explicitly labelled editorial assumptions retain source, market and check date; they do not take minimum and maximum values across all matching bottles. Short/long format and reviewed nonstandard row volumes require a static full recipe fingerprint plus source and version identity. Unreviewed quantities and unknown selected-bottle strengths remain missing. Only ml and US fl oz convert generically; explicit row overrides and melting-water ml describe the displayed whole batch. The default estimate is before ice, with dilution shown only after explicit water input. Format is an independent editorial classification, with rationale, and is absent for an unmatched snapshot.

Making analysis preserves v1 exact matching and v2 frozen candidate, brand and actual supply bindings. An actual bottle must still contain its frozen bound ingredient, even when another source-row alternative remains allowed; brand reference ranges use only matching examples. Recipe details simulate locally. Making reuses existing assumptions and checked optional rows, with a single save for batch inputs; completed sessions are read-only. No new storage key, recipe identity, backup schema, catalogue mapping or dependency is introduced.

Taste learning is an in-memory view derived from successfully persisted feedback, with no new business storage or backup schema. The latest observation of each version ID plus frozen recipe fingerprint counts once. Discovery fits a 120-coordinate Bayesian ridge utility model from at most the latest 1,000 preference-bearing snapshots: whole-recipe likes/dislikes and lower-weight explicit flavour/adjustment observations. Frozen ingredient IDs, ingredient/flavour pairs and known comparable ratios share evidence; absent historical metadata is never backfilled. All individual ingredient IDs are represented, while pair work is bounded to the first 32 sorted required IDs and quantities are aggregated once. Hash collisions limit the model; explanations use actual raw overlaps, never inferred hash associations. Missing selections, neutral sentiment, browsing, experience marks and private notes are not preference labels. Utilities and posterior deviations are internal, uncalibrated values.

Discovery preserves the full searchable catalogue and adds five posterior-mean/MMR picks plus one quality-gated, previously unrecorded cocktail selected using a shared Thompson posterior draw. Hard filters constrain exact source versions before selection; cocktail IDs are deduplicated. Cold starts and limited pools are labelled honestly. A session-only seed, explicit exploration round and last exploration ID preserve the slate across detail returns, reloads and pagination; requesting another exploration retains the first five. Reasons start collapsed and expose one concise explanation with at most one real feedback link. Text search and list-selection flows keep the ordinary catalogue. Read failures leave browsing usable; failed writes keep the saved model and disable feedback links until retry. Guided search leaves memory off by default and retains its optional bounded adjustment. The separate descriptive profile reports explicit signal support, not the Bayesian coefficients or accuracy. Edits, deletion, undo, clear and backup restore rebuild derived views.

Full backup export uses schema 3 and reads schemas 1, 2 and 3. Individual sections are independently versioned. Full backup files are limited to 50,000,000 UTF-8 bytes; each serialized category and the reference section retain their 5,000,000-byte limits. Private recipe JPEG data URLs are included and count toward these limits. Restore previews changes, uses recipe fingerprints for semantic identity, checks the exact raw before-state and storage generation before committing, keeps before-images, journals writes, verifies readback and invalidates stale writers. Selected restored bottles, favourites, private recipes, making sessions and taste experiences must pass their normal storage parsers and size limits before journal writes begin, including after merging. Missing sections in an older backup must not erase newer data. Backups are not encrypted.

Full schema 3 now exports an optional shopping section. Older backups without it cannot select or erase local shopping, even in replace mode. Merge preserves bought status and frozen OR choices, retaining conflicting targets without identity collisions and validating the merged after-image before journal writes. The new reader accepts older backups; older application binaries reject backups containing the new section because their readers enforce exact keys.

Every personal-data write holds the shared browser Web Lock, advances a verified storage generation before the write, and blocks stale windows until reload. Without Web Locks, browser personal-data writes and restore fail visibly; use HTTPS or localhost in a supported browser. The desktop host retains its single-process serialization. Browser storage belongs to its origin. A domain or protocol change does not move that data; export and restore explicitly. Desktop host storage belongs to the stable application identifier `com.glassnotes.desktop`, in each operating system's application-data directory.

## Desktop boundary

Five host commands expose whitelisted local storage and bounded import/export dialogs. Host code owns filesystem paths. Business storage and laboratory files retain a 5,000,000-byte limit; full-backup dialogs allow 50,000,000 bytes and restore still checks each category's smaller limit. The 23 permitted keys must stay aligned between TypeScript and Rust, including shopping and recovery slots 0–10. Preserve the local-origin checks, capabilities, CSP and single-instance behaviour; do not add arbitrary filesystem access.

Windows uses a current-user NSIS installer. macOS merges `tauri.macos.conf.json` to produce an app and DMG for macOS 12+, with ad-hoc signing; release builds combine arm64 and x86_64. Both platforms share the same host and local-file contract. Desktop release CI checks Rust storage behaviour, Windows installation/upgrade and macOS bundle integrity before uploading build artifacts. Publishing remains separate from building, and no automatic updater is configured.

The Windows automated upgrade baseline defaults to 1.0.0 and preserves a raw marker file; the disposable-runner script also accepts an explicit older baseline tag. macOS CI verifies the bundle and launch without replacing an old installed copy. Follow the [desktop acceptance guide](DESKTOP-ACCEPTANCE.md) to verify an upgrade from the current public version with valid personal records, photos, revisions and subsequent writes. Record each actually tested OS/architecture; packaging checks alone do not establish business-data preservation.

## Presentation

Mobile and desktop browsers share routes and rules. Responsive styles adjust layout without changing stored data. Motion respects pause, reduced motion and background state. The Liquid G assets and `src/theme/tokens.ts` define the existing identity.

The presentation uses deep green, ivory Songti/serif display type, ruled editorial rows and sage actions. Web/Tauri create the procedural Three.js coupe after hydration when first entering a scene that displays it; direct links to utility pages avoid GPU initialization and shader warm-up. Once created, the same coupe and orbital composition stay mounted across routes, pause on inactive scenes and dispose with the shell. Typography uses local fonts and works offline; recipe imagery and provenance remain catalogue inputs.

The coupe measures synchronous render cost and the next animation-frame interval after each actual draw. Two consecutive renders over 40 ms, or two post-draw frame intervals over 100 ms, lower its pixel ratio, including on DPR 1 displays, down to 0.5; costly frames also leave up to 100 ms before the next render so input and other animations can run. Cheap frames reserved for input are not counted as rendered samples. Fast renderers retain their initial resolution and cadence. Colour and flavour transitions follow actual active elapsed time across slow frames; only spring integration caps its step at 50 ms. Pause and resume exclude paused time from those transitions. Geometry, materials and presentation state stay the same; limited hardware trades image sharpness for responsiveness. An isolated shader/GC spike does not lower resolution. Browser CI records its actual graphics backend; software-rendered checks do not replace manual desktop GPU acceptance.

Guided results compose the ranked sequence by count: one hero, a pair, a trio, four in two rows, five with a centred final pair, and six in two rows of three. Narrow screens use two columns after the single hero. Partial rows remain centred; layout never changes the ranking or selected recipe version.

Web and the Tauri webview use GSAP with `@gsap/react` in the shared `.web` motion adapters. Default modules re-export those adapters and preserve their shared types. Scoped `useGSAP` contexts clean up route/step transitions and event callbacks. Animate transforms and opacity, release temporary layer promotion, and avoid outgoing DOM clones or per-frame layout measurements. Result filters commit immediately and stagger at most eight cards, with a control to skip the entrance. System motion preferences use a shared ready snapshot; an unresolved preference cannot consume a newly mounted entrance. Cross-route photos use one captured canvas texture and a batched destination measurement; navigation, pause, scroll, resize and destination reflow interrupt the flight and restore the live image. The captured texture lives directly in the viewport; destination measurement waits for local fonts and scroll restoration. Loop playheads pause when offscreen, backgrounded or user-paused. Modal portals open directly and preserve their keyboard focus contract. Browser motion regression checks are in `scripts/check-transitions.playwright.js`.

Route and question changes commit immediately while foreground entrances overlap the background's slower movement. Web/Tauri guided progress and actions remain in the stable frame, and the guided choice tree remains mounted through its departure; result cards become accessible at their entrance, with a separate skip control available during the cup sequence. Outgoing titles and cross-route photos use bounded canvas textures from the live heading and existing local image; React retains ownership of every semantic node. The relay preserves source-version routes and destination controls. A photo is concealed before its destination mounts; its captured hover crop bridges to the destination and remains there until the live image decodes. Cold route contents acknowledge an entrance only when real targets mount; photo geometry is read after route scroll restoration. Hidden zero-width measurements cannot replace a results layout. Workflow state never waits for animation completion. An interruption lands the current view and clears temporary presentation state.

The home archive draws three different drinks with reviewed local media and valid default versions on each fresh visit. Resizing and changing language retain the selection, as does returning from an archive recipe, so the shared photo has a stable return destination. Both phone and desktop show all three entries, with two-line captions. Desktop home navigation follows the editorial entries in document flow with at least 32px of clearance; short windows scroll instead of overlapping controls. Phone navigation retains its inset bottom bar.

Foreground choreography excludes retained hidden routes and gives question grids and result entrances one animation owner. The ambient space bridges committed endpoints using transforms; the canvas measures its untransformed size, warms shaders asynchronously and can lower pixel density under sustained frame pressure while keeping the motion cadence.

Web export produces `dist`; desktop preparation copies that export into a separate build directory. Community, accounts and cloud synchronisation are not required for this architecture.

The local web sensory coupe uses the approved aroma study: six procedural garnishes, blended liquid colours and persistent, bounded taste/body/first-sip waves. Strength affects amplitude rather than elapsed-time frequency. A single thin glass wall avoids rotated transparency seams. The result reveal keeps live outgoing React content until its fade finishes, solidifies the same persistent coupe, centres it, turns it once with damped liquid inertia, then fades it before decoded results rise into view. Search commits immediately; pause, reduced motion, skip, route changes and resize settle presentation without changing matching or personal data. Filled secondary panels keep their own horizontal padding and readable form widths.

## Verification and development network

`npm run validate` runs TypeScript, the Node test suite, Web export, real Chromium E2E checks at desktop/phone widths. Install the locked browser with `npm run browser:install` first. E2E tests operate on a loopback static export with fresh browser profiles and synthetic records; they verify persistence, backup/restore, stale-window protection, source-version navigation and filter keyboard focus. Making checks wait for mounted route controls and store hydration before starting their business assertions; a deliberately held cross-tab storage lock verifies cold-start waiting, error blocking and recovery. They do not establish physical phone-browser or Windows/macOS installation compatibility. The existing motion script remains a broader manual regression check.

Mobile acceptance uses the actual hosted website on target phone browsers: verify layout, navigation, Web Locks/storage, photo selection and backup import/download over HTTPS. Mobile file/photo and storage adapters use the same browser implementation as desktop Web; Tauri keeps its narrow host bridge.

Project Expo commands start the Web target on loopback by default and reject native launch/export and direct tunnel flags. To check phones on a trusted network, use the static `preview:lan` website. Expo remains the Web bundler/router; its transitive packages are not evidence of a supported native mobile target.


## Maintained inputs and generated output

`assets/brand` is the sole brand maintenance directory. Web and desktop commands prepare their required icons automatically; `brand:check` regenerates missing outputs while checking maintained inputs against the manifest. Comparison previews stay under ignored `artifacts/brand`. These generated paths are excluded from public source exports and validation source snapshots; the manifest, generator and maintained inputs remain part of the source checks.

Git does not retain the `public` directory when it contains only ignored brand outputs. Validation treats an absent, empty or generated-only `public` root equally, while still hashing all maintained public files and rejecting symlinked or invalid roots. A fresh checkout can therefore generate icons during validation without a false source-change failure.

`research` holds reviewed maintenance inputs and content-test evidence; its [index](../research/README.md) explains each group. The ingredient source selection preserves source records and reviewed choices, while ordered translation overlays distinguish source-derived drafts from editorial edits. Builder worksheets and reports go to ignored `artifacts/ingredients`. Runtime data is checked in so starting or building the app does not re-run content authoring.

Content filenames describe their responsibility. Some persisted IDs retain historical suffixes such as `-batch-m`; changing those IDs would break saved version references and is separate from renaming source files.
